# Lector architecture

Lector is a reading-first code viewer and git review tool with light editing, written in Rust on
GPUI. It opens a folder, shows code, diffs, history and review queues, edits and saves files,
stages, commits and syncs with a remote, hosts an integrated terminal and drives coding agents.
The same headless core serves the GUI, a command line (`lector <subcommand>`) and an MCP server
(`lector mcp`). It writes to the user's files or repository only when the user asks.

**How to read this document.** It describes the system as it is on this branch, top-down:
principles, the layers, one short section per crate, the flows that cross crates, the security
rules, the conventions and the guardrails. It names types and functions as rustdoc paths
(`lector_app::store::Store`); their contracts live in the rustdoc next to the code
(`cargo doc --no-deps -p <crate> --open`). Decisions and their reasons live in
[`docs/adr/`](adr/README.md); this document links to them instead of restating them. There is no
version history here: see `CHANGELOG.md`.

## Principles

These are the rules that actually constrain code. Each names what enforces it.

1. **UI-free core.** Every crate except `lector` and the `lector-ui*` crates builds and tests
   without GPUI, a window system or tokio; `lector-cli` and `lector-mcp` additionally stay free
   of GPUI because they ship as a console binary. *Enforced by* `arch-check deps` (the
   `[closure]` lists in `arch/layers.toml`).
2. **Strict layering.** A crate depends only on crates in lower layers. *Enforced by*
   `arch-check deps` and the generated graph below (`arch-check graph --check`).
3. **One stateful layer.** Only `lector-app` holds state between calls, starts work or writes;
   `lector-review` is a pure function of its inputs ([ADR 0001](adr/0001-one-app-layer.md)).
   *Enforced by* `arch-check purity`.
4. **Every write is a registry command.** Changes to the user's files, index, refs, stashes,
   remotes or config go through `lector_app::CommandRegistry::invoke`, which journals them and
   declares their undo ([ADR 0002](adr/0002-one-write-path.md)). *Enforced by*
   `arch-check writes`, `crates/lector-app/tests/undo_roundtrip.rs` and
   `crates/lector-agent/tests/undo_declarations.rs`.
5. **Reads never write.** Opening, browsing, refreshing, diffing, blame and history leave the
   repository byte- and mtime-identical. *Enforced by* `crates/lector-app/tests/read_only.rs`
   (every non-writing command) and `crates/lector-app/tests/release_audit.rs`.
6. **One scheduler, named threads.** Short background work runs on `lector_app::Scheduler`;
   long-lived resources get owner threads from `lector_base::thread::spawn_named` with a kind from
   a closed list ([ADR 0003](adr/0003-one-scheduler.md)). *Enforced by* `arch-check threads`
   and `arch-check background`.
7. **One state store.** Lector's own state lives in one versioned database behind
   `lector_app::store` ([ADR 0004](adr/0004-one-state-store.md)). *Enforced by*
   `arch-check state` and `crates/lector-app/tests/state_upgrade.rs`.
8. **One cancel token, one fuzzy scorer.** `lector_base::CancelToken` and `lector_base::fuzzy`
   ([ADR 0005](adr/0005-base-crate.md)); long work takes a token and returns early when it is
   set. *Enforced by* `arch-check dupes`.
9. **Snapshots, not locks.** Text is immutable and cheap to clone (`lector_text::Text`); background
   work runs on a snapshot and its result carries the snapshot's version, so stale results are
   dropped. *By review.*
10. **Never panic on user data.** Libraries return `thiserror` errors, binaries use `anyhow`; no
    `unwrap`/`expect` on user data or I/O. *Enforced by* `arch-check hygiene` (ratcheted count).
11. **Small files.** Hand-written source files stay under 1,500 lines
    ([ADR 0006](adr/0006-file-size.md)). *Enforced by* `arch-check size`.
12. **Every user command is a GPUI action.** Key bindings, the palette, menus and context menus
    dispatch the same action (`lector_ui::actions`); registry commands are listed once.
    *Enforced by* the `command_palette_rows_are_unique_and_guarded` and
    `every_palette_action_is_in_a_menu` tests in `lector-ui`.

**What each layer may depend on** (`arch/layers.toml`; normal and build dependencies count,
dev-dependencies do not). *base* (`lector-base`) depends on nothing but std and every crate may
use it. *leaf* crates depend on nothing internal except `lector-base`. *service* crates build on
leaves. *analysis* holds the stateless `lector-review` and the dev-only `lector-perf`; for
`lector-review` the edges to `lector-app`, `lector-agent` and `lector-ui*` are also explicit
`[[forbid]]` entries.
*app* is `lector-app` alone. *client* (`lector-agent`, `lector-mcp`, `lector-ui`) consumes the app;
*frontend*, *ui-agent* and *binary* sit on top. No `lector-ui*` crate may depend on
`lector-process` (UI code never spawns processes), and the removed `lector-workspace` may not come
back (`[[forbid_crate]]`). An edge between two crates of one layer needs a `[[same_layer]]` entry;
there are none. Only `lector` and `lector-ui*` may reach GPUI, window-system or async-runtime
crates; `lector-cli` and `lector-mcp` may not reach GPUI. Moving a crate or changing a rule here
needs an ADR.

## Crates

Each section: purpose, what it owns, what it must not do, and where a newcomer starts reading.
API detail is in rustdoc.

### lector-base (base)
The bottom layer: one cancel token, one fuzzy scorer, named threads. **Owns** cancellation
(child tokens, `on_cancel` hooks), the fuzzy ranking used by every picker except the file finder,
and the registry of owner threads. **Must not** depend on anything but std, or schedule work.
**Start at** `lector_base::CancelToken`, `lector_base::fuzzy::Matcher`, `lector_base::fuzzy::Query`,
`lector_base::thread::spawn_named`, `lector_base::thread::TaskRunner`.

### lector-archcheck (leaf)
The architecture checker behind `scripts/arch-check` (a dev tool, not shipped). **Owns** the rules
in [Guardrails](#guardrails), the baseline ratchet and the generated crate graph. **Must not**
grow dependencies beyond `serde_json` (for `cargo metadata`) and `toml` (its config files). **Start at** `lector_archcheck::run`,
`lector_archcheck::rules`, `lector_archcheck::baseline`.

### lector-config (leaf)
Paths, settings and key maps. **Owns** `settings.toml` parsing with the user and project layers,
`keymap.toml`, the data/config directory layout (portable mode and the `LECTOR_CONFIG_DIR` /
`LECTOR_DATA_DIR` overrides) and the update-check policy. **Must not** store Lector's own state
(that is `lector_app::store`) or let a project layer set user-only keys. **Start at**
`lector_config::paths`, `lector_config::load_settings_for`, `lector_config::Settings`,
`lector_config::load_keymap`, `lector_config::should_check_now`.

### lector-diff (leaf)
Line diffs and everything derived from them, on plain strings. **Owns** `imara-diff` line
diffs, word/char refinement, split and unified row models, context folding, gutter marks,
moved-code detection, line remapping and re-anchoring, and patch building for partial staging.
**Must not** know about git or files. **Start at** `lector_diff::diff_lines`,
`lector_diff::refine_inline`, `lector_diff::split_rows`, `lector_diff::moves`,
`lector_diff::remap::LineMap`, `lector_diff::patch::build_patch`.

### lector-forge (leaf)
Code hosts (GitHub, GitLab) and the update check, over blocking HTTPS (`ureq`, rustls). **Owns**
remote detection, token lookup (environment, `gh`/`glab`, OS keychain), pull requests, review
threads and submissions, and `releases` (release list, minisign verification, install kind).
**Must not** open files for its state (callers persist `releases::UpdateState`) or log tokens.
**Start at** `lector_forge::detect`, `lector_forge::auth_token`, `lector_forge::connect`,
`lector_forge::Forge`, `lector_forge::releases::check_for_update_with`.

### lector-icons (leaf)
File and UI icons as embedded SVG bytes. **Owns** the Material Icon Theme mapping (generated into
`src/generated.rs` by `scripts/gen_icons.py`) and the Lucide UI icons. **Must not** be edited by
hand in `generated.rs`. **Start at** `lector_icons::FileIcons`, `lector_icons::UiIcon`,
`lector_icons::ui_icon`.

### lector-process (leaf)
Every child process Lector starts, as a supervised process tree (a new session on Unix, a Job
Object on Windows). **Owns** spawning, streaming output, cancellation and timeouts, killing whole
trees, the quit-time shutdown of children, and the askpass credential server and helper. **Must
not** be used by UI crates (ADR 0002) or run anything through a shell. **Start at**
`lector_process::ProcessCommand`, `lector_process::Supervisor`, `lector_process::run`,
`lector_process::ChildHandle`, `lector_process::askpass::AskpassServer`.

### lector-search (leaf)
Finding files and text. **Owns** the parallel gitignore-aware walker, project grep and in-text
find/replace, the trigram index, and the file finder's streaming `Picker` (scored by nucleo, ADR
0005). **Must not** offer a general fuzzy function (that is `lector-base`). **Start at**
`lector_search::walk_files`, `lector_search::search_project`, `lector_search::find_in_text`,
`lector_search::Picker`, `lector_search::TrigramIndex`.

### lector-terminal (leaf)
The UI-free core of the integrated terminal: PTY (`portable-pty`) plus VT emulator
(`alacritty_terminal`). **Owns** sessions, snapshots with damage, input encoding, links, shell
integration (OSC 7/133) and killing the shell's process tree. **Must not** expose alacritty or
portable-pty types, or execute anything a program prints. **Start at**
`lector_terminal::Terminal`, `lector_terminal::SpawnOptions`, `lector_terminal::Emulator`,
`lector_terminal::Snapshot`, `lector_terminal::TerminalEvent`.

### lector-text (leaf)
Text storage. **Owns** the copy-on-write `SumTree`, the `Rope`, memory-mapped read-only text for
huge files, and coordinate conversions (bytes, `Point`, UTF-16). **Must not** depend on any
internal crate; it is the only crate allowed `unsafe` (the memory map, `arch/unsafe.allow`).
**Start at** `lector_text::Text`, `lector_text::Rope`, `lector_text::MappedText`,
`lector_text::Point`, `lector_text::sum_tree::SumTree`.

### lector-theme (leaf)
Theme model and the four built-in themes (dark, light, two high-contrast). **Owns** colors,
syntax capture styles, user TOML themes and WCAG contrast checks. **Must not** depend on GPUI.
**Start at** `lector_theme::ThemeRegistry`, `lector_theme::Theme`, `lector_theme::Color`.

### lector-buffer (service)
The UI-free editing model. **Owns** multi-caret selections, typing rules (auto-close, indent,
type-over), undo history with coalescing, edit deltas for tree-sitter and LSP, and encoding text
back to bytes for saving. **Must not** touch files or GPUI. **Start at** `lector_buffer::Buffer`,
`lector_buffer::Transaction`, `lector_buffer::TextEdit`, `lector_buffer::save::encode`.

### lector-fs (service)
File loading and watching. **Owns** kind detection (text, binary, image), decoding (UTF-8,
UTF-16 BOM, windows-1252 fallback), mmap thresholds, the debounced watcher, atomic writes and file
stamps. **Must not** write anything except through `write_atomic`, which only explicit saves
reach. **Start at** `lector_fs::load_file`, `lector_fs::detect_kind`, `lector_fs::watch`,
`lector_fs::write_atomic`, `lector_fs::stamp`.

### lector-git (service)
Git: reads through `gix`, writes and network operations through the git CLI under
`lector-process`. **Owns** status, changesets, blobs, log, graph, blame and line history, the
write API (`write`, `sync`, branches, stashes, conflict operations) and the shadow repository
(Lector's own bare repository for backups, agent checkpoints and pull-request fetches). **Must
not** be called for writes except from `lector-app` registry commands (`arch-check writes`), or
write into the user's `.git` from the shadow. **Start at** `lector_git::Repo`,
`lector_git::Changeset`, `lector_git::write`, `lector_git::sync`, `lector_git::ShadowRepo`.

### lector-lsp (service)
A runtime-agnostic language-server client. **Owns** one server per (root, server), lazy start and
restart, document sync, navigation, diagnostics, formatting, code actions, rename, completion and
signature-help sessions, and the "no writes into the project" server options. **Must not** write
files: edits come back as data for the caller to apply to buffers. **Start at**
`lector_lsp::LspManager`, `lector_lsp::ServerConfig`, `lector_lsp::CompletionSession`,
`lector_lsp::SignatureSession`, `lector_lsp::RequestOutcome`.

### lector-syntax (service)
Tree-sitter. **Owns** the language registry and detection, parsing (incremental through
`Syntax::edit_and_reparse`), highlights with injections, outline, folds, brackets, tags and the
tags-based symbol index. Grammar provenance is in `crates/lector-syntax/GRAMMARS.md`. **Must not**
depend on anything but `lector-text`. **Start at** `lector_syntax::LanguageRegistry`,
`lector_syntax::Syntax`, `lector_syntax::SymbolIndex`, `lector_syntax::HighlightId`.

### lector-perf (analysis)
The instruction-count gates (`scripts/perf-gate.sh`, `perf/baseline.json`; not shipped). **Owns**
one gate binary per core crate and the callgrind runner. **Must not** be a dependency of shipped
code. **Start at** `lector_perf::harness`, `lector_perf::runner`, `docs/PERFORMANCE.md`.

### lector-review (analysis)
Stateless review analysis ([ADR 0001](adr/0001-one-app-layer.md)). **Owns** changeset loading and
keys, file diffs, hunk patches (computed, not applied), risk facts and scoring, structural diff,
conflict-marker parsing and resolution edits. **Must not** keep state across calls, start
detached threads, cache, or write anything (`arch-check purity`); viewed marks come in as an input
and caching goes through the `DerivedCache` it is given. **Start at**
`lector_review::review::load_changeset_with`, `lector_review::review::FileDiff`,
`lector_review::risk::assess`, `lector_review::structural::diff`,
`lector_review::conflicts::parse_conflicts`, `lector_review::content::DerivedCache`.

### lector-app (app)
The headless core and the only stateful layer. **Owns** the `AppCore` (scheduler, command
registry, journal, state store, git service, document store), the open project, documents,
commands, undo, the content cache, review data, provenance, comments, crash log and session
health, and the quit sequence. **Must not** depend on GPUI or tokio, or on `lector-forge`.
**Start at** `lector_app::AppCore`, `lector_app::CommandRegistry`, `lector_app::Scheduler`,
`lector_app::store::Store`, `lector_app::documents::DocumentStore`, `lector_app::journal::Journal`.

### lector-agent (client)
Coding agents over the Agent Client Protocol (newline-delimited JSON-RPC on the agent's stdio).
**Owns** sessions and turns, permission requests, agent file reads and writes through the document
store, turn checkpoints in the shadow repository, undo of a turn, the agent provenance provider,
inline-edit state and turn summaries. **Must not** let an agent read or write outside the project
or in `.git`, or give it a terminal or Lector's tools. **Start at** `lector_agent::AgentSession`,
`lector_agent::AgentManager`, `lector_agent::rpc::Connection`, `lector_agent::inline_edit`,
`lector_agent::summary::TurnSummary`.

### lector-mcp (client)
The Model Context Protocol server behind `lector mcp` (JSON-RPC over stdio, no tokio). **Owns**
mapping registry commands to tools and documents/changesets to resources. **Must not** write to
stdout anything but protocol messages, or list or run writing commands without `--allow-writes`.
**Start at** `lector_mcp::McpServer`, `lector_mcp::ServerOptions`.

### lector-ui (client)
The GPUI shell: workspace, panes, code view, editor, pickers, menus, themes, accessibility.
**Owns** the one bridge from UI code to the scheduler (`background`), the bridge to the command
registry (`commands_bridge`), the extension seams other UI crates register into, and the GPUI
adapter over the document store. **Must not** spawn processes, call the `lector-git` write API or
start background work other than through `lector_ui::background`. **Start at** `lector_ui::init`,
`lector_ui::views::Workspace`, `lector_ui::code_view::CodeView`, `lector_ui::editor::FileView`,
`lector_ui::background::background`, `lector_ui::commands_bridge`.

### lector-cli (frontend)
The headless command line (`lector status | changes | diff | commands | run | activity | undo |
mcp | health`) and the console binary `lector-cli`. **Owns** argument parsing, human and `--json`
output (stable schemas, documented in the crate's rustdoc), exit codes and the askpass helper
entry. **Must not** depend on GPUI. **Start at** `lector_cli::is_cli_invocation`,
`lector_cli::run_args`, `lector_cli::run_askpass_helper`.

### lector-ui-git (frontend)
Git views: Changes panel, diff and review tabs, history with graph, branches, blame, merge
editor, sync control and dialogs, credential prompts, pull requests and review comments.
**Owns** the per-window `GitStore` over the shared `RepoState`, and the UI flows that front git
commands (confirmations, progress, Undo toasts). **Must not** write except by invoking registry
commands (`staging::run_op`, `sync::SyncController`). **Start at** `lector_ui_git::init`,
`lector_ui_git::store::GitStore`, `lector_ui_git::staging::run_op`,
`lector_ui_git::diff_view::DiffView`, `lector_ui_git::review_tab::ReviewView`.

### lector-ui-terminal (frontend)
The integrated terminal's panel, tabs, splits, rendering, key routing and session restore.
**Owns** frame scheduling (one snapshot per painted frame), lazy restore and link routing. **Must
not** write to a terminal on its own. **Start at** `lector_ui_terminal::init`,
`lector_ui_terminal::TerminalPanel`, `lector_ui_terminal::TerminalView`.

### lector-ui-agent (ui-agent)
The Agent panel, inline agent edit, turn summary cards, the update dialog and the crash-log
dialog. **Owns** the update-check schedule and the one-time questions (`notices::Notices` in the
state store). **Must not** download or run anything for an update. **Start at**
`lector_ui_agent::init`, `lector_ui_agent::AgentPanel`, `lector_ui_agent::inline_edit`,
`lector_ui_agent::update_model`, `lector_ui_agent::notices::Notices`.

### lector (binary)
The `lector` executable. `main` dispatches in this order: the askpass helper
(`lector_cli::run_askpass_helper`), CLI/MCP subcommands (`lector_cli::is_cli_invocation`), then
the GUI: panic hook (`lector_app::health::install_panic_hook`), session health, settings and the
project on the scheduler while GPUI starts, `lector_ui::init` and the extension crates' `init`,
and the quit hook that runs `lector_app::shutdown::shutdown` last. Logging goes to stderr and
`lector_config::paths::log_file`, rotated at 4 MiB.

## Cross-cutting flows

### A write to the user's files or repository
1. The user acts: a button, menu item, key binding or palette row. UI code never calls the
   `lector-git` write API; it builds a command id and JSON arguments. Git panels go through
   `lector_ui_git::staging::run_op` (a `GitOp` maps to a command), sync and branch flows through
   `lector_ui_git::sync::SyncController`, other actions through
   `lector_ui::commands_bridge::invoke`. A palette row for a destructive or not-undoable command
   with no UI flow asks first (`commands_bridge::needs_confirmation`, `invoke_from_palette`).
2. The invocation runs as a scheduler job (`CommandRegistry::invoke_async`: `JobKind::Command`
   for writes; the git panels use `GitWrite`, sync flows `NetworkCommand`) and calls
   `lector_app::CommandRegistry::invoke` with a `CommandContext` whose `source` is `Source::Ui`.
3. `invoke` is the one enforcement point: it refuses a `Sources::UiOnly` command for any other
   source, validates the arguments against the spec's JSON schema (`commands::schema`), checks
   availability, then calls `Command::apply`. Commands confine path arguments from sandboxed
   sources (MCP, agents) to the project (`CommandContext::confine_path`).
4. The command (for example in `lector_app::commands::git_write` or `git_sync`) backs up what it
   will overwrite into the shadow repository (`lector_git::ShadowRepo::snapshot_paths` /
   `snapshot_index`) and refuses with `BackupUnavailable` if it cannot, unless the caller allowed
   it after asking the user. It then calls the `lector-git` write API (git CLI) and returns an
   `Outcome` with an `UndoRecord`.
5. For `writes` specs `invoke` records an `ActivityRecord` through the `ActivitySink`, which is
   the `lector_app::journal::Journal`; the entry id lands in `Outcome::journal_id`.
6. Back on the UI thread, `commands_bridge::apply_outcome` applies `UiRequest`s and the git
   views refresh (`RepoState::refresh_and_notify`); an outcome with an undo record is toasted as
   "… · Undo" (`commands_bridge::set_undo_offer`).
7. Undo (the toast, `workspace::UndoLastOperation`, the Activity log, `lector undo`) calls
   `Journal::undo` with `UndoMode::Check`: it refuses with `UndoError::Changed` if the files changed
   since; `UndoMode::Force` ("Restore anyway") backs up the present state first, so every undo is
   itself undoable.

Saving a file is the other write: `DocHandle::save` (see [Opening and editing a document](#opening-and-editing-a-document)) encodes the buffer and calls
`lector_fs::write_atomic`. Discards and other overwrites are backed up and undoable instead of
confirmed; what still confirms is listed under [Write policy](#write-policy). Every write command
declares `undo: Undoable | NotUndoable(reason)`; `crates/lector-app/tests/undo_roundtrip.rs`
enumerates the registry and round-trips each undoable one.

### A background job
1. UI code calls `lector_ui::background::background(cx, key, priority, f)` (or `detach`). The key
   is a `lector_app::JobKey`: a `JobKind` from the closed list in `lector_app::scheduler::key`
   plus a `Subject` (a document, repository, view, path…). `lector_ui::background` is the only
   module allowed to touch GPUI's executors (`arch/background.allow`).
2. The scheduler (`lector_app::Scheduler::global()`, shared with the CLI and `lector mcp`) puts
   the job on the lane its kind declares (`JobKind::lane`): **compute** (general workers plus one
   worker reserved for the few kinds that may be `Interactive`), **blocking** (waits on the
   network, a language server or an external program; bounded by `BLOCKING_MAX`) or **guaranteed**
   (askpass prompts, agent requests and turns, cancel/undo, terminal kill: always start at once).
3. A newer job with the same key replaces an older one for kinds that `replaces()`; closing a
   subject (`Scheduler::cancel_subject`, called when a document, a `RepoState` or a view is
   dropped; `background::cancel_on_release` for windows) cancels its jobs, except writes.
4. The job runs with a `lector_base::CancelToken`; a panic is caught and becomes
   `JobError::Panicked`.
5. The result is delivered on the main thread as a `BackgroundTask<T>` future of
   `Result<T, JobError>`. A job stays registered under its key and subject until its result is
   taken or dropped, and delivery checks and unregisters in one step, so a job replaced or
   cancelled after it finished still never delivers. Dropping the task cancels the job
   synchronously.
6. Below `lector-app`, crates do not schedule: they expose blocking, cancellable functions, and an
   owner thread with short work to hand off calls a `lector_base::thread::TaskRunner` its caller
   supplies (`Scheduler::task_runner`). A runner takes the task or hands it back for the caller
   to run inline; a task is never silently dropped.
7. Quit (`lector_app::shutdown::shutdown` with `QuitBounds::default()`): cancel every non-write job
   and refuse new ones (`Scheduler::begin_quit`), drain writes (`Scheduler::drain`: 10 s, network
   writes 2 s) while child processes are alive, stop every supervised process tree
   (`Supervisor::shutdown`), stop the scheduler. Writes given up on are reported in the
   `ShutdownReport` and the crash log. Terminals are killed by their own quit hook before this
   (`lector_ui_terminal::kill_all`); each kill escalation is a `TerminalKill` job the drain waits
   for.

Lanes, kinds, priorities and the quit policy per kind are in the rustdoc of
`lector_app::scheduler` and `lector_app::scheduler::key`; the decision is
[ADR 0003](adr/0003-one-scheduler.md).

### A credential prompt (askpass)
1. A network git command (fetch, pull, push) is started by a `git_sync` command. `SyncHost`
   (`lector_app::commands::git_sync::SyncHost`, an `AppCore` extension) owns one
   `lector_process::askpass::AskpassServer` per process, started on first use with
   `SyncHost::start_askpass(runtime_dir, handler)`; the UI supplies only the handler
   (`lector_ui_git::askpass_ui`) and the runtime directory (`lector_config::paths::data_dir` by
   default).
2. The server listens on a Unix socket in a fresh `0700` directory (loopback TCP on Windows) and
   holds a 256-bit token. `SyncHost` puts the helper program and the endpoint, token and operation
   id into the environment of that git process only (`GIT_ASKPASS`, `SSH_ASKPASS`,
   `SSH_ASKPASS_REQUIRE=force`, `GIT_TERMINAL_PROMPT=0`, `LECTOR_ASKPASS_*`); configured
   credential helpers still answer first.
3. git or ssh runs the helper: a `0700` shell shim that execs `lector --lector-askpass-helper`
   (Unix), or a hard link named `lector-askpass.exe` (Windows). `main` hands it to
   `lector_cli::run_askpass_helper` before anything else; the environment alone never selects
   helper mode (`lector_process::askpass::askpass_prompt_from_args`).
4. The helper connects, authenticates with the token and sends the prompt
   (`lector_process::askpass::run_askpass_client`). The server hands the connection to the
   scheduler's guaranteed lane (`JobKind::AskpassPrompt`) through its `TaskRunner`.
5. The handler classifies the untrusted prompt text (`parse_prompt`, `classify_prompt`,
   `sanitize_prompt_text`), posts to the GPUI thread and blocks (at most
   `askpass_ui::PROMPT_TIMEOUT`) while one dialog at a time asks the user. Passwords are masked,
   held in `Secret` (zeroed, never logged or stored by Lector); an unknown host key defaults to
   Cancel and answers exactly `yes`.
6. The answer (or Cancel, also when the window closes or the operation is cancelled) goes back to
   git. On quit the server and its directory are removed (`SyncHost::shutdown_askpass`).
   Terminals, language servers and agents never see the askpass variables
   (`lector_process::askpass::SCRUB_ENV`, `lector_terminal::shell::DEFAULT_ENV_SCRUB`).

### An agent turn
1. The Agent panel (`lector_ui_agent::AgentPanel`) or a front-end invokes `agent.start` /
   `agent.prompt` (`lector_agent::commands`). `AgentManager::of(&core)` starts an `AgentSession`:
   an agent from the **user's** `[[agent.servers]]` or a known ACP agent found on `PATH`
   (`lector_agent::available_configs`; a project cannot add one), as a supervised process tree
   (`ProcessKind::Agent`, askpass variables scrubbed).
2. `AgentSession::prompt` starts a turn as a `JobKind::AgentTurn` job (guaranteed lane). The turn
   takes a "before" checkpoint (`ShadowRepo::snapshot_worktree`), sends `session/prompt` with the
   context blocks, and streams `session/update` notifications into the `Turn`.
3. Agent-to-client requests run as `JobKind::AgentRequest` tasks
   (`lector_agent::rpc::Connection`). `fs/read_text_file` serves the open document (unsaved edits
   included) or the file; `fs/write_text_file` goes through the open `DocHandle` or
   `lector_fs::write_atomic`. Both are confined to the project root and refused in `.git`
   (`lector_agent::paths::resolve_in_root`). Each write is journaled as `agent.write_file` with
   `Source::Agent`.
4. `session/request_permission` becomes a `PermissionRequest` shown inline in the panel; the user
   answers allow once / always for the session / reject (`AgentSession::answer_permission`).
   `auto_allow_reads` answers reads inside the project. Cancel answers pending requests
   `cancelled`.
5. When the turn ends an "after" checkpoint is taken; a turn that changed files appends one
   `agent.turn` journal entry whose undo restores the "before" snapshot
   (`AgentSession::undo_turn` → `Journal::undo`). The turn's changes are a
   `lector_git::Changeset::Snapshots` reviewable in the normal review tab.

**What each source can reach.** The agent itself gets no terminal (`terminal: false`), no MCP
servers and none of Lector's commands: only file reads and writes inside the project, each
journaled, and permission prompts. MCP clients see the registry minus `writes` commands unless
`lector mcp --allow-writes`, with path arguments confined (`Source::Mcp`). `lector run` refuses a
writing command without `--allow-writes`. A command marked `Sources::UiOnly` (for example
`review.fetch_pull_request`, which uses the user's credentials and the network) is refused for the
CLI, MCP and agents and omitted from their listings (`CommandRegistry::list_for`). Turning a
UI-only capability into a command must not widen this ([ADR 0002](adr/0002-one-write-path.md)).

### State: where Lector keeps its own data
1. **Files people edit** stay files in `lector_config::paths::config_dir()`: `settings.toml`,
   `keymap.toml`, themes; plus a project's `.lector/settings.toml`. Logs and crash reports stay
   files in the data directory (`lector_app::health`) so they work when the database does not.
   The shadow repositories (`data_dir()/shadow/`) and shell-integration scripts are files too.
2. **Everything else** lives in `data_dir()/lector.redb` behind `lector_app::store::Store`: one
   table per concern (recent projects, window and terminal sessions, review marks, notices,
   update state), each with a schema version in `store_meta`, plus the comments, journal, `kv` and
   content-cache tables on `lector_app::db::Db`. Every write is one transaction; processes share
   the file (redb `MultiWriter`).
3. **Opening** (`Store::open`, never fails): a newer schema is detected through a read-only handle
   first and never opened for writing. If the file cannot be opened for writing, the process runs
   with `StoreMode::ReadOnly`: an in-memory copy, never written back. That state stays visible: a
   status bar item (`StoreMode::indicator`), a startup toast, a line in `lector health`
   (`Store::probe`, which creates and changes nothing and answers what `Store::open` would do), and one stderr line from headless commands at the first write
   (`StoreMode::headless_warning`).
4. **Recovery:** a file that stays corrupt over repeated opens is renamed aside to an owner-only
   `lector.redb.corrupt-<secs>` under a cross-process lock, and a fresh database is created
   (`Store::recovered_from`; the UI says so).
5. **Import:** the JSON files of 0.3–0.7.1 are imported once per file and renamed to
   `*.imported` (`Store::import_legacy`); never in read-only state.

Rustdoc: `lector_app::store` (concern table), `lector_app::store::open`,
`lector_app::store::legacy`. Decision: [ADR 0004](adr/0004-one-state-store.md).

### Opening and editing a document
1. A file tab (`lector_ui::editor::FileView`) asks `lector_app::documents::DocumentStore` (the
   `AppCore`'s, `DocumentStore::for_core`) to open the path through the bridge
   (`JobKind::DocumentOpen`). There is one live document per canonical path, shared by every view,
   window, agent and command.
2. `lector_fs::load_file` detects the kind and decoding; files over the mmap threshold become
   `lector_text::Text::Mapped` (read-only), others a `Rope`. `LanguageRegistry::language_for_path`
   picks the grammar and `lector_syntax::Syntax` parses; the first screen's highlights are computed
   before the first paint.
3. The tab's `lector_ui::editor::DocumentModel` (the GPUI adapter) wraps the `DocHandle` in an
   `EditBuffer`; `CodeView` renders through a `CodeSource` (`DocumentSource` for files).
4. Typing: `CodeView::edit` runs a `lector_buffer::Buffer` operation through
   `DocHandle::edit_from`, which returns the `Transaction` plus edits other front-ends made
   meanwhile. Every edit gets a `seq`; other views map their carets through it.
5. Derived data are versioned queries on the scheduler: an incremental reparse
   (`Syntax::edit_and_reparse`), highlight chunks, outline and folds after typing stops, the diff
   gutter against HEAD, blame mapped onto the buffer, LSP sync (`LspManager::open_document_tagged`
   with the rope version as tag) and diagnostics mapped through edits. Stale results are dropped
   by version.
6. Saving (`DocHandle::save`, `JobKind::DocumentSave`): before-save hooks (format on save), cleanup
   edits as buffer edits, `lector_buffer::save::encode` with the file's encoding and line ending, a
   stamp check (`DocError::ChangedOnDisk` unless forced), `lector_fs::write_atomic`.
7. External changes (watcher → `DocHandle::check_disk`): a clean document reloads, a dirty one
   becomes a `DiskConflict` (Reload / Keep mine / Compare), a deleted file is tracked.

## Security rules

The reasons behind these rules are in [ADR 0009](adr/0009-security-posture.md).

### Write policy
Lector writes to the user's files or repository **only** as the direct result of an explicit user
action: save, stage/unstage, commit, discard, resolve, accept an LSP edit into the buffer and then
save, sync, branch and stash operations. Nothing writes on open, on focus, on a timer or as a side
effect of reading.
- **Opt-in automation only.** Auto-save, format-on-save, automatic fetch (`git.auto_fetch`) and
  update checks (`[updates] check`) are off by default and user-level settings only.
- **Undo instead of confirm.** Destructive operations back up what they lose into the shadow
  repository first and show an Undo toast; `git.confirm_discard = true` brings the confirmation
  back. A confirmation remains when the backup cannot be taken, for operations that cannot be
  undone or reach beyond the machine (abort a merge or rebase, force push with lease, submit a
  review), before deleting an unmerged branch, and for closing or reloading unsaved buffers. Undo never silently throws away newer edits.
  Backups are pruned after 30 days or above 1 GiB per repository.
- **Git writes go through the git CLI** (`lector_git::write`, `lector_git::sync`) so hooks, locks,
  filters and signing behave as in a terminal; reads stay on gix with `GIT_OPTIONAL_LOCKS=0`.
- **Saves are atomic** (temp file, fsync, rename), keep permissions, encoding and line endings,
  and refuse to overwrite a file changed on disk unless the user confirms.
- **Language servers** start with options that keep them from writing into the project
  (`lector_lsp::read_only_settings`); servers known to write (`lector_lsp::WRITES_TO_PROJECT`) run
  only when the user enables them. Their edits are applied to buffers, never to files.
- **Lector's own state** lives in `lector_config::paths::data_dir()` / `config_dir()` and in the
  shadow repositories there, never in the user's `.git`.

### What leaves the machine
Only these network requests exist, all through `lector-forge` (HTTPS, rustls with the platform
verifier, proxies from the environment) or the git CLI:
- **Code hosts**, when the user works with pull requests (the Pull Requests panel, review
  threads, submitting a review): GitHub or GitLab APIs with the user's token. A project's `.lector/settings.toml` cannot set `[forge]`, so a
  repository cannot send the token elsewhere. Pull-request heads are fetched into the shadow
  repository, never the user's.
- **The update check**, only when enabled or asked for: one unauthenticated request to the GitHub
  releases API (no identifiers), at most once a day. A release is "verified" only when the
  minisign signature of `SHA256SUMS.txt` checks against the key compiled in from
  `packaging/update-key.pub` and its trusted comment names that tag; Lector never downloads or
  runs an update. Rustdoc: `lector_forge::releases`; release signing: `docs/RELEASING.md`.
- **git network commands** the user starts (fetch, pull, push) or opts into (`git.auto_fetch`).
- Crash reports and session health stay local (`lector health`); nothing is uploaded. Markdown
  preview does not fetch remote images. Agents and language servers are separate programs the
  user configured; what they do on the network is theirs.

### Credentials
Tokens come from the environment, `gh`/`glab` or the OS keychain (`lector_forge::auth_token`);
`Token`'s `Debug` is redacted and tokens are never logged. git credentials go through the user's
credential helpers first, then Lector's askpass prompt (flow above): answers are `Secret`s,
zeroed, never stored by Lector; the endpoint and token reach only the git process's environment.
Remote URLs shown to the user are redacted (`lector_git::sync::redact_credentials`). The pull-request
fetch passes its auth header through `GIT_CONFIG_*` environment variables, never argv.

### Spawning processes
UI crates start no processes (ADR 0002): they invoke `lector-app` commands and services
(`lector_app::os` for "reveal in file manager"; URLs open through GPUI), and the terminal panel
spawns shells through `lector-terminal`. Long-lived and network children run under
`lector_process::Supervisor`, each in its own process tree, stopped at quit. A few short-lived
helpers use `std::process` directly: git writes and the shadow repository (so tty signing
pinentries work), the terminal's PTY and kill helpers, the `gh` / `glab` token lookup, the
liveness probes of the health log and the askpass sweep (`ps`, `tasklist`), and `lector.com`
starting the GUI. Nothing runs through a shell: arguments are separate argv entries, git paths
come after `--` with `--literal-pathspecs`, data goes through stdin. `settings.toml` of a project cannot choose a
program: language-server commands, agent commands, `[forge]`, `[updates]`, `git.auto_fetch` and
the terminal's shell and safety keys are user-only (`lector_config` drops them from the project
layer with a warning).

### File permissions
A new `lector.redb` is created `0600`; a damaged one is made `0600` before it is moved aside. The
askpass directory is `0700`, its socket and helper shim owner-only. `write_atomic` keeps the
target's permissions and refuses a read-only target.

### Untrusted input
- **Repositories** are data: nothing in a repository runs on open; read paths are tested not to
  write; conflict markers, diffs and file names never panic (proptests in `lector-review`,
  `lector-buffer`, `lector-diff`).
- **Archives and binaries** are detected and shown as such; files over the size limits are not
  parsed (`lector_syntax::MAX_PARSE_BYTES`, `lector_review::review::MAX_DIFF_BYTES`); non-regular
  files are refused instead of blocking.
- **Language servers**: `workspace/applyEdit` is validated against synced versions and applied to
  buffers only, all or nothing; file operations in workspace edits are refused.
- **Agents**: confined to the project, journaled, permission-gated; prompts and tool output are
  displayed, never executed.
- **Prompt text** from ssh and git is classified only by exact templates; anything else is shown
  sanitized as "Other".
- **Forge responses**: URLs opened from the update dialog must be on the project's GitHub
  release pages (`lector_ui_agent::update_model::safe_release_url`).

### Terminal
Lector never writes to a terminal on its own: no auto-run, "Open in Terminal" only sets the folder.
OSC 52 clipboard reads are denied and copies land only while that terminal is focused; titles and
folder names are stripped of control and bidi characters; only `http`, `https` and `mailto` links
open, file links open locked read-only when outside the project; pastes are sanitized and a
multi-line paste without bracketed paste asks first. Agents get no terminal access. Rustdoc:
`lector_terminal` and `lector_ui_terminal`.

## Conventions

- **Coordinates.** Byte offsets are `usize` (UTF-8). Line numbers in APIs are 0-based `u32`; the UI
  adds 1. `lector_text::Point { row, column }` counts the column in bytes;
  `lector_text::PointUtf16` in UTF-16 code units (LSP). Ranges are half-open `[start, end)`. The
  one exception: the terminal's `lector_terminal::GridPoint` has a signed line (negative lines are
  scrollback). The CLI's `--json` and MCP outputs use the same 0-based lines.
- **Errors.** Libraries define `thiserror` enums (each with a `Cancelled` variant where long work
  takes a token, `From<lector_base::Cancelled>`); the binaries and UI glue use `anyhow`. Nothing
  panics on user data; a panic in a scheduler job is caught and reported.
- **Threads.** The GPUI main thread owns entities and never runs git, process or multi-file work
  in render, menu building or an action handler; it reads cached values and starts jobs through
  the bridge. Core crates are synchronous and cancellable; `rayon` and `std::thread::scope` inside
  one call are fine; long-lived threads only via `spawn_named`.
- **Unsafe.** `#![forbid(unsafe_code)]` in every crate root except `lector-text`, where each
  `unsafe` block carries a `// SAFETY:` comment. The `lector-perf` gate binaries are the remaining
  baselined exceptions in `arch/baseline.toml`.
- **Tests** live next to the code (`#[cfg(test)]`) plus `tests/` for integration; `proptest` for
  invariants, `insta` for snapshots, `tempfile` for fixtures; git fixtures are built with the
  `git` CLI with a hermetic config. Write commands need an undo round trip; read commands are
  covered by `tests/read_only.rs`. Fake servers (`tests/fixtures/*.py`, `fake_acp_agent.py`,
  `lector_forge::mock::MockServer`) stand in for language servers, agents and code hosts.
  A crate whose GPUI tests start background work enables `lector-ui`'s `test-support` feature and
  asserts `lector_ui::background::is_test_dispatcher`, so jobs run on the test executor.
- **Performance.** Budgets below; instruction-count gates run in CI on Linux
  (`scripts/perf-gate.sh` against `perf/baseline.json`). Measurements and how to reproduce them:
  [`docs/PERFORMANCE.md`](PERFORMANCE.md).
- **Releasing.** Packaging, signing and the update key: [`docs/RELEASING.md`](RELEASING.md).
- **Accessibility.** What is supported and the known gaps: [`docs/ACCESSIBILITY.md`](ACCESSIBILITY.md).

## Guardrails

`scripts/arch-check` (crate `lector-archcheck`) runs in CI on every pull request together with
`cargo fmt`, `cargo clippy -D warnings`, the test suite on Linux, macOS and Windows, `cargo deny`
and the instruction-count gates. Existing violations are a ratchet in `arch/baseline.toml`: counts
may only fall, and must be lowered in the same pull request (`scripts/arch-check --update`).
Running and extending it: [`arch/README.md`](../arch/README.md);
design: [ADR 0008](adr/0008-guardrails.md).

| Rule | What it enforces | Allow file |
|---|---|---|
| `deps` | Layering, forbidden edges and crates, GUI/tokio closures | `arch/layers.toml` (an ADR, not an allowance) |
| `writes` | No call of the `lector-git` write API outside `lector-app` commands | `arch/git-read.allow`, `arch/git-ambiguous.allow` |
| `threads` | Threads only through `lector_base::thread`; closed `spawn_named` kinds | `arch/threads.allow` |
| `background` | GPUI executors only in the UI bridge | `arch/background.allow` |
| `state` | No state files built under the data/config dirs outside the store | `arch/state.allow` |
| `dupes` | One `CancelToken`, one fuzzy matcher | none |
| `size` | Hand-written files at most 1,500 lines | `arch/generated.allow` |
| `purity` | `lector-review` keeps no state, starts no threads, writes nothing | `arch/review-statics.allow`, `arch/store-ambiguous.allow` |
| `hygiene` | `forbid(unsafe_code)`, `// SAFETY:` comments, `unwrap`/`expect` ratchet | `arch/unsafe.allow` |
| `graph` | The crate graph above matches `cargo metadata` | none |

**Changing a decision.** Structural decisions are ADRs in `docs/adr/`, written before the code and
never rewritten: a changed decision is a new record that supersedes the old one
([process](adr/README.md)). Builders implement to a record and stop and report if it is wrong.
An allowance needs a reason comment and a reviewer; a change to `arch/layers.toml` or a raised
baseline needs an ADR. A public API change to something described here updates this document;
API detail goes in rustdoc.
