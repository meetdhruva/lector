# Releasing Lector

Releases are built entirely by GitHub Actions (`.github/workflows/release.yml`).

## Cutting a release

1. Bump `version` in `[workspace.package]` of the root `Cargo.toml`, run `cargo check -p lector-cli`
   (updates `Cargo.lock`), and turn the `## <version> — unreleased` heading in `CHANGELOG.md` into
   `## <version> — <date>`. Update the `<releases>` list in
   `packaging/linux/io.github.meetdhruva.Lector.metainfo.xml` (each release has a `<url type="details">` to its
   GitHub release page and the release date). The winget, cask and Flatpak templates take the version from the
   release job and need no edit. Before the first signed release, set up the `release` environment
   ([Trust boundaries](#trust-boundaries-jobs-the-release-environment-pinned-tools)).
2. Commit, push to `main`, wait for CI to pass.
3. Tag and push: `git tag -a v0.2.0 -m "Lector 0.2.0" && git push origin v0.2.0`.
   Alternatively run **Actions → Release → Run workflow** with the tag; it is created at the
   selected commit. Tags containing `-` (e.g. `v0.2.0-beta.1`) are published as pre-releases.
4. Check the release page: the notes' **Signing** table says what was signed (generated from what the
   jobs actually did), and the release carries `SHA256SUMS.txt`, its `.minisig` (when signed),
   `lector.rb`, `Lector-<version>-winget-manifests.zip` and `io.github.meetdhruva.Lector.yml`.
5. Package managers: see [Package managers](#package-managers).

The `prepare` job fails fast if the tag does not match the workspace version.

### Dry runs

Push any `release/**` branch (e.g. `git push origin HEAD:release/v0.2.0`) to build every
artifact exactly as a release would, without publishing: the files are attached to the
workflow run as artifacts (`dist-linux-x86_64`, `dist-macos-universal`, ...), plus `release-preview`
(`SHA256SUMS.txt`, the package-manager files, the release notes). CI also runs
on `release/**` branches, so the full test suite runs on Linux, macOS and Windows first.

**Dry runs never sign or notarize** (that would burn notarization / Azure signing quota and use secrets for
nothing); their notes say "not signed". To test signing without publishing, run **Actions → Release → Run
workflow** with `dry_run` and `sign_dry_run` both ticked: everything is built, signed and notarized, and
nothing is published (the checksum signature is made too; the release-preview artifact shows the result).
Do this once after adding or changing any signing secret.

## What gets built

| Job | Runner | Artifacts |
|---|---|---|
| Linux x86_64 | ubuntu-22.04 (glibc 2.35) | `.deb`, `.rpm`, `.AppImage`, portable `.tar.gz` (+ `.asc` signatures when signed) |
| Linux aarch64 | ubuntu-22.04-arm | same |
| macOS universal | macos-latest (arm64 + x86_64 cross, `lipo`) | `.dmg`, `.zip` (`Lector.app`: Developer ID signed + notarized when configured, otherwise ad-hoc signed) |
| Windows x64 | windows-latest | Inno Setup `setup.exe`, WiX `.msi`, portable `.zip` (Authenticode-signed when configured) |
| Windows arm64 | windows-latest (cross-compiled) | same |
| Checksums, sign checksums, publish | ubuntu-latest | `SHA256SUMS.txt` (+ `.minisig`), `lector.rb`, `Lector-<v>-winget-manifests.zip`, `io.github.meetdhruva.Lector.yml`, the GitHub release |

Each platform is several jobs, split at the trust boundary (next section): `linux`/`macos`/`windows` build and package
without secrets; `sign-linux`, `macos-package`, `sign-windows-binaries` and `sign-windows-installers` sign;
`checksums` (no secrets), `sign-checksums` and `publish` finish. Intermediate artifacts are named `unsigned-*`,
`macos-universal-binary`, `windows-bin-*`; the release files are the `dist-*` artifacts.

Binaries use the `dist` profile (thin LTO, one codegen unit, stripped). Every artifact
contains the licenses, `README.md`, `CHANGELOG.md` and `third-party/` notices, including
the full license texts of all Rust dependencies generated by `cargo about` (`about.toml`,
`about.hbs`).

## Packaging locally

```sh
cargo build --profile dist -p lector -p lector-cli   # lector-cli: the Windows console build, see below
cargo about generate --workspace about.hbs -o target/THIRD_PARTY_CRATES.md   # optional
scripts/package-linux.sh target/dist/lector 0.3.0 x86_64 dist        # needs dpkg-deb; rpmbuild/appimagetool optional
scripts/package-macos.sh target/dist/lector 0.3.0 aarch64 dist       # on macOS; unsigned (ad-hoc) unless LECTOR_MACOS_SIGN=1
pwsh scripts/package-windows.ps1 -Binary target\dist\lector.exe -CliBinary target\dist\lector-cli.exe -Version 0.3.0 -Arch x64 -OutDir dist
scripts/gen-package-manifests.sh 0.3.0 dist manifests   # Homebrew cask, winget manifests, Flatpak manifest from the files in dist/
```

## Command line on Windows (`lector-cli.exe`, `lector.com`)

Release builds of `lector.exe` use the GUI subsystem, so a terminal gives it no console (and `cmd.exe`
does not wait for it). Lector's subcommands (`lector status`, `changes`, `diff`, `commands`, `run`,
`activity`, `undo`, `mcp`) therefore need a console-subsystem executable. We ship one instead of calling
`AttachConsole` from the GUI binary:

* `crates/lector-cli` is a library plus the binary `lector-cli`. It has **no GUI dependencies** (much
  smaller than `lector.exe`, starts in a few milliseconds) and no `unsafe` code, so the workspace
  keeps its single sanctioned `unsafe` exception (`lector-text`).
* The Windows packages (portable zip, Inno Setup, MSI) install it twice: `lector-cli.exe`, and a copy named
  **`lector.com`**. In `cmd.exe` and PowerShell a bare `lector` resolves `.com` before `.exe` (`PATHEXT`),
  so `lector status` runs in the terminal with a real console, synchronously, and `lector mcp` works as an
  MCP server command. `lector .` / `lector path\to\file:12` (no subcommand) make `lector.com` start the
  GUI `lector.exe` next to it, detached, and return immediately.
* `lector.exe` itself also handles the subcommands (shared code): it works when its stdio is redirected
  (`lector.exe mcp` from an MCP client, `lector.exe status > out.txt`), just not interactively.
* Linux and macOS do not need it: `lector` is a normal console-capable executable there and dispatches the
  subcommands before any GUI code runs. Only the Windows job builds and packages `lector-cli`.
* The release workflow smoke-tests `lector-cli.exe --version` and `status --json` on the x64 build.

## Signing

Nothing here is required to build a release. **No certificates have been bought yet**, so today every release is
unsigned and says so. Each signing step turns itself on when its secrets exist, and the release notes' **Signing**
table is generated from what really happened in the run.

How the workflow decides: every job has a "Signing credentials" step that maps the secrets to environment variables
and writes `enabled=true|false` (or `provider=azure|pfx|none`) as a step output; later steps test that output (GitHub
does not expose secrets to `if:`). Signing is also off when the run is a dry run (see above). Third-party actions
added for signing: none (plain scripts: `scripts/sign-macos.sh`, `sign-windows.ps1`, `sign-linux.sh`,
`sign-checksums.sh`); every action in the workflow is pinned by full commit SHA (version in a trailing comment).

### Trust boundaries: jobs, the `release` environment, pinned tools

The workflow separates jobs that run downloaded code from jobs that hold secrets:

* **Build and package jobs hold no secrets.** They run the Rust toolchain, `cargo-about`, `appimagetool`, `choco`,
  WiX and the like. `appimagetool` is a tagged release (`APPIMAGETOOL_VERSION`) verified against a SHA-256 in the
  workflow `env:` (to bump it, download the new assets, run `sha256sum`, update the three values).
* **Signing and publishing jobs** (`sign-linux`, `macos-package`, `sign-windows-binaries`,
  `sign-windows-installers`, `sign-checksums`, `publish`, `winget`) hold the secrets and run only this repository's
  scripts, GitHub's own artifact actions, preinstalled tools and distribution packages (`minisign`, `rpm`). Two
  exceptions run downloaded code next to credentials: the Azure signing client (a NuGet package signtool loads; pin
  it by adding the repository **variable** `ARTIFACT_SIGNING_CLIENT_SHA256` with the hash that
  `scripts/sign-windows.ps1` prints on a first run; without it the job warns) and `wingetcreate` (pinned release,
  SHA-256 checked, in the `winget` job). `publish` also runs `softprops/action-gh-release`, pinned by SHA.
* **Secrets go in an environment.** These jobs declare `environment: release` (`release-preview`, which never holds
  secrets, when the run is a dry run that does not sign or publish, so previews never wait for an approval). One-time
  setup for the maintainer:
  1. Settings → Environments → **New environment** → `release`.
  2. Enable **Required reviewers** (you, plus a second person when there is one), and restrict **Deployment branches
     and tags** to `main` and `v*` tags.
  3. Move every signing secret and token from Actions repository secrets into that environment's secrets (the
     list is in the workflow header), and delete the repository-level copies. The `ARTIFACT_SIGNING_CLIENT_SHA256`
     variable can live in the environment too.
  4. A release then pauses at the first signing job until a reviewer approves; later signing jobs may ask again as
     they are reached, and approving a "Waiting" list covers all jobs waiting at that moment.

  The workflow still works with no environment, or one without protection rules: GitHub creates `release` on first
  use and the jobs just run (secrets in repository settings are visible to them as before). The early update-key
  check in `prepare` only sees a *repository* secret; with the secret in the environment it is skipped there and
  `scripts/sign-checksums.sh` refuses the placeholder public key at the end of the run instead.
* Passwords that end up on a command line (`security import -P`, `signtool /p`) are masked with `::add-mask::`
  first.

### Secrets to create

GitHub → repository **Settings → Environments → `release` → Environment secrets** (preferred, see
[Trust boundaries](#trust-boundaries-jobs-the-release-environment-pinned-tools)) or **Settings → Secrets and
variables → Actions → New repository secret**. All optional; unset secrets simply leave that platform unsigned. (Hardening: protect the `v*` tag pattern and `release/**`
branches with a ruleset so only maintainers can trigger runs that can read secrets.)

**macOS** (needs all of the first two; the three `APPLE_API_*` enable notarization — without them the app is signed
but not notarized, which Gatekeeper still rejects for downloaded apps, so treat that as incomplete):

| Secret | Contains | How |
|---|---|---|
| `MACOS_CERTIFICATE_P12_BASE64` | the **Developer ID Application** certificate with its private key, as `.p12`, base64 | developer.apple.com → Certificates → **+** → *Developer ID Application* (account holder only; upload a CSR made in Keychain Access → Certificate Assistant). Install the downloaded `.cer`, then Keychain Access → *My Certificates* → right-click the certificate → *Export…* → `.p12` with a password. `base64 -i cert.p12 \| pbcopy` (macOS). Delete the `.p12` afterwards. |
| `MACOS_CERTIFICATE_PASSWORD` | the password chosen for that `.p12` | |
| `MACOS_SIGNING_IDENTITY` *(optional)* | exact identity, e.g. `Developer ID Application: Your Name (TEAMID)` | only needed if the `.p12` holds several identities; otherwise the first Developer ID Application identity is used |
| `APPLE_API_KEY_P8_BASE64` | the App Store Connect API key (`AuthKey_XXXXXXXX.p8`), base64 | appstoreconnect.apple.com → *Users and Access* → *Integrations* → *App Store Connect API* → *Team Keys* → generate a key (role *Developer* is enough for `notarytool`); the `.p8` can be downloaded **once**. `base64 -i AuthKey_XXXXXXXX.p8 \| pbcopy` |
| `APPLE_API_KEY_ID` | the key's **Key ID** | shown next to the key |
| `APPLE_API_ISSUER_ID` | the **Issuer ID** (a UUID) | shown at the top of the same page |

**Windows**, option A — Azure Artifact Signing (preferred; all six must be set):

| Secret | Contains |
|---|---|
| `AZURE_TENANT_ID` | Directory (tenant) ID of the Entra ID tenant |
| `AZURE_CLIENT_ID` | Application (client) ID of an app registration used as service principal |
| `AZURE_CLIENT_SECRET` | a client secret of that app registration (they expire, at most 24 months: put a reminder in the calendar) |
| `AZURE_SIGNING_ENDPOINT` | the account's regional endpoint, e.g. `https://eus.codesigning.azure.net` (**must match the region of the account and the profile**, a mismatch shows up as HTTP 403) |
| `AZURE_SIGNING_ACCOUNT` | the Artifact Signing account name |
| `AZURE_SIGNING_PROFILE` | the certificate profile name (type *Public Trust*, identity validation completed) |

Setup: Azure portal → register the `Microsoft.CodeSigning` resource provider → create the signing account → *Identity
validation* → create a *Certificate profile* → *Access control (IAM)*: give the service principal the role
**Artifact Signing Certificate Profile Signer** (formerly *Trusted Signing Certificate Profile Signer*). The workflow
uses `signtool` with `Azure.CodeSigning.Dlib.dll` from the NuGet package `Microsoft.ArtifactSigning.Client`
(version pinned in `scripts/sign-windows.ps1`, overridable with the `ARTIFACT_SIGNING_CLIENT_VERSION` environment
variable) and the timestamp server `http://timestamp.acs.microsoft.com`. Microsoft also publishes a GitHub Action
for this service; it is not used so that one script signs binaries and installers the same way.

Option B — a certificate file (only if you already hold one as a file, see the cost table):

| Secret | Contains | How |
|---|---|---|
| `WINDOWS_CERTIFICATE_PFX_BASE64` | the `.pfx`, base64 | PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("cert.pfx")) \| Set-Clipboard` (or `base64 -w0 cert.pfx`) |
| `WINDOWS_CERTIFICATE_PASSWORD` | its password | |
| `WINDOWS_TIMESTAMP_URL` *(optional)* | RFC 3161 server, default `http://timestamp.digicert.com` | |

If both options are configured, Azure wins. The workflow signs `lector.exe` and `lector-cli.exe` **before** packaging
(so the portable zip, the Inno installer and the MSI contain signed binaries; `lector.com` is a byte copy of the signed
`lector-cli.exe`) and the `setup.exe` and `.msi` **after** packaging, with SHA-256 and an RFC 3161 timestamp, then runs
`signtool verify /pa`. Not done: the Inno uninstaller (`unins000.exe`, created at install time) is not signed
(Inno's `SignedUninstaller` would need a sign-tool command registered with `ISCC`).

**Linux** (GPG):

| Secret | Contains | How |
|---|---|---|
| `LINUX_GPG_PRIVATE_KEY_BASE64` | an ASCII-armored **secret** key, base64 | `gpg --quick-generate-key "Lector releases <you@example.org>" ed25519 sign 3y`, then `gpg --armor --export-secret-keys <FINGERPRINT> \| base64 -w0` |
| `LINUX_GPG_PASSPHRASE` *(optional)* | its passphrase | |

Also publish the **public** key where users can fetch it: `gpg --armor --export <FINGERPRINT> > packaging/linux/lector-release-key.asc`
(commit it), and upload it to keys.openpgp.org. The release notes print the fingerprint that signed that release.
The workflow signs the tarball, AppImage, `.deb` and `.rpm` (detached `.asc`, verified immediately) and tries to
embed a signature in the `.rpm` too (`rpmsign`; best effort, reported in the notes when it worked).

**All platforms — update signing key** (the project's own trust anchor, independent of Apple, Microsoft and GitHub):

```sh
scripts/gen-update-key.sh ~/lector-release-keys --install-public-key   # key directory must be outside the repository
git add packaging/update-key.pub && git commit    # the public key is compiled into Lector
```

| Secret | Contains |
|---|---|
| `UPDATE_SIGNING_KEY` | the full contents of `lector-update.key` (the secret key file, two lines of text) |
| `UPDATE_SIGNING_KEY_PASSWORD` | its password (leave the secret out if you created the key with `--no-password`) |

Back the key up offline in two places; delete it from the machine that generated it. Until the public key is committed,
`packaging/update-key.pub` is a placeholder and Lector treats every download as **not verified** (it never claims
verification without a key); the workflow refuses to sign while the secret is set but the file is still the placeholder
(`prepare` job, so you learn it before the two-hour build). Rotating the key requires shipping a Lector release
with the new public key *before* releases signed with it can be verified.
The signature is `SHA256SUMS.txt.minisig` (minisign, prehashed Ed25519, trusted comment `lector vX.Y.Z`).

**Package managers** (optional pushes; the manifests are attached to the release either way):

| Secret | Contains |
|---|---|
| `HOMEBREW_TAP_TOKEN` | fine-grained personal access token with *Contents: read and write* on `meetdhruva/homebrew-tap`; the workflow commits `Casks/lector.rb` for non-pre-release, non-draft releases |
| `WINGET_TOKEN` | classic personal access token with `public_repo`; the `winget` job runs `wingetcreate update` to open the pull request on microsoft/winget-pkgs |

### Verifying a signed release

* **macOS**: `codesign --verify --deep --strict --verbose=2 /Applications/Lector.app`; `codesign -dvv /Applications/Lector.app`
  shows `Authority=Developer ID Application: …` and the Team ID; `spctl -a -vv /Applications/Lector.app` should say
  `accepted` / `source=Notarized Developer ID`; `xcrun stapler validate Lector-<v>-macos-universal.dmg`.
* **Windows**: `signtool verify /pa /v Lector-<v>-windows-x64-setup.exe`, or PowerShell
  `Get-AuthenticodeSignature .\Lector-<v>-windows-x64-setup.exe | Format-List` (Status `Valid`, plus the timestamp);
  Explorer → Properties → *Digital Signatures*. Same for the `.msi`, `lector.exe` and `lector-cli.exe`.
* **Linux**: `gpg --import lector-release-key.asc && gpg --verify lector_<v>_amd64.deb.asc lector_<v>_amd64.deb`
  (the fingerprint must match the one in the release notes); for an `.rpm`: `rpm --import lector-release-key.asc && rpm -K lector-<v>-1.x86_64.rpm`.
* **Checksums (all platforms)**, with [minisign](https://jedisct1.github.io/minisign/) and the key committed in
  `packaging/update-key.pub` (second line of that file):
  `minisign -Vm SHA256SUMS.txt -P <public key>` (must print `Trusted comment: lector v<version>`), then
  `sha256sum -c SHA256SUMS.txt --ignore-missing`. This is what Lector's update check does.

## Package managers

All three manifests are generated at release time by `scripts/gen-package-manifests.sh` from the templates in
`packaging/homebrew/`, `packaging/winget/` and `packaging/flatpak/` and attached to the GitHub release.

### Homebrew cask (`lector.rb`)

One-time setup: create the repository **`meetdhruva/homebrew-tap`** (the `homebrew-` prefix is required) with a
`Casks/` folder. Users then run `brew install --cask meetdhruva/tap/lector`. Each release: copy the attached
`lector.rb` to `Casks/lector.rb` and push — or set `HOMEBREW_TAP_TOKEN` and the workflow does it. Check a new cask with
`brew audit --cask --online --strict meetdhruva/tap/lector` and `brew style`. While the macOS build is not notarized the cask
shows a caveat explaining the first-launch confirmation (the generator removes it for notarized releases). The cask
does not strip the quarantine attribute for the user. Submitting to the main `homebrew-cask` repository is a separate
step, and its rules about unsigned or un-notarized apps have been tightening; read their current policy first.

### winget

Manifests use schema **1.6.0** (version, installer, defaultLocale) for the Inno Setup installers (x64 and arm64) with
the Inno `ProductCode` (`{AppId}_is1`). They were validated against Microsoft's published 1.6.0 JSON schemas with a
JSON-schema validator, **not** with `winget` itself (not available here). First submission is manual:

1. Unzip `Lector-<v>-winget-manifests.zip` into a fork of microsoft/winget-pkgs at `manifests/m/meetdhruva/Lector/<v>/`.
2. `winget validate --manifest <that folder>`; optionally `winget settings --enable LocalManifestFiles` then
   `winget install --manifest <that folder>` (or use the Windows Sandbox script in winget-pkgs).
3. Open the pull request; the bot runs validation, a Defender scan and a test install. Unsigned installers are more
   likely to be flagged for manual review.

Later versions: `wingetcreate update meetdhruva.Lector --version <v> --urls <x64 url>\|x64 <arm64 url>\|arm64 --submit --token <PAT>`,
which is exactly what the optional `winget` job runs when `WINGET_TOKEN` is set (not exercised yet; it needs the first
manifest to be merged). winget cannot tell a winget install from a direct installer run, so the update check on
Windows shows the `winget upgrade meetdhruva.Lector` command as a hint next to the download.

### Flatpak

`io.github.meetdhruva.Lector.yml` (runtime `org.freedesktop.Platform` 25.08, check the current runtime version) builds
from the release tarball (prebuilt binaries, `./install.sh /app`), for x86_64 and aarch64, using the app id, desktop
file and AppStream metainfo of `packaging/linux`. Build locally:

```sh
flatpak install flathub org.freedesktop.Platform//25.08 org.freedesktop.Sdk//25.08
flatpak-builder --user --install --force-clean build-dir io.github.meetdhruva.Lector.yml
flatpak run io.github.meetdhruva.Lector
```

Permissions (`finish-args`): Wayland with X11 fallback (`--socket=wayland`, `--socket=fallback-x11`, `--share=ipc`),
`--device=dri` (Vulkan/GL rendering), `--share=network` (pull-request review, the opt-in update check) and
**`--filesystem=host`**. Trade-off: a code viewer has to open projects anywhere, which is why editors ask for the
whole filesystem, but it means the sandbox no longer protects your files from Lector; narrower options are
`--filesystem=home` (misses `/mnt`, `/srv`, other disks) or no filesystem permission at all (open folders with the
file chooser portal, one folder at a time; worktrees and symlinks leaving the folder are not reachable).

**Plain limitation: host tools are not visible inside the sandbox.** Lector shells out to `git` for all git features
and to language servers (`rust-analyzer`, `gopls`, ...) for code intelligence. The freedesktop runtime has no git and
the host's programs are not on the sandbox's `PATH`, so inside this Flatpak most review features do not work until
git is added to the manifest (a module building git from a verified source tarball; not included because it could not
be built and tested here) and language servers are unavailable unless bundled too. The integrated terminal
runs a shell *inside* the sandbox. `flatpak-spawn --host` would run host programs, but it needs
`--talk-name=org.freedesktop.Flatpak`, which is a complete sandbox escape (anything in the sandbox could then run
arbitrary commands on the host). The manifest does **not** grant it, and Lector does not use `flatpak-spawn`
today; users who accept the risk can `flatpak override --user --talk-name=org.freedesktop.Flatpak io.github.meetdhruva.Lector`
(which changes nothing until Lector learns to use it). Token storage in the OS keychain (kernel keyutils) is probably
blocked by the Flatpak seccomp filter (untested); use `GITHUB_TOKEN` / `GITLAB_TOKEN` instead.

Not Flathub-ready: Flathub requires building from source (vendored Cargo sources, no network during the build).
This manifest is for sideloading and as a starting point. The update check detects the Flatpak sandbox and shows
`flatpak update io.github.meetdhruva.Lector` instead of a download.

## Update check

Lector's opt-in update check (`[updates]` in `settings.toml`, `lector_forge::releases`) reads the GitHub Releases API,
and verifies `SHA256SUMS.txt` with `packaging/update-key.pub`; the contract and trust model are in
`docs/ARCHITECTURE.md` ("Updates and signing (v0.7)"). It depends on this pipeline's file names
(`Lector-<v>-macos-universal.dmg`, `…-windows-<arch>-setup.exe`, `lector_<v>_<arch>.deb`, ...,
`SHA256SUMS.txt`, `SHA256SUMS.txt.minisig`): renaming artifacts means updating `select_asset` in
`crates/lector-forge/src/releases.rs` and its tests.

## Known gaps and things not tested

What follows could not be run where the signing and packaging work was done (Linux, no macOS, Windows,
Apple/Azure accounts, `pwsh`, `actionlint`, `flatpak-builder`, `winget`, or GitHub Actions itself). Treat the first
signed run as an experiment: do the `dry_run` + `sign_dry_run` run first.

* **Workflow**: YAML parsed and cross-checked (job `needs`, step outputs, secrets, expression balance), every bash
  `run:` block passed `shellcheck`, but `actionlint` was not available and nothing ran on GitHub. PowerShell steps and
  `scripts/sign-windows.ps1` were reviewed by hand only.
* **macOS**: `scripts/sign-macos.sh` is only syntax- and shellcheck-checked (no `codesign`, `security`, `notarytool`
  here). The empty entitlements file is a judgement (no JIT, no sandbox, no plug-ins); if a signed build fails to start,
  look in Console.app before adding entitlements.
* **Windows**: the Azure Artifact Signing NuGet package version and layout (`Microsoft.ArtifactSigning.Client`, the
  x64 `Azure.CodeSigning.Dlib.dll`) come from Microsoft's documentation and a search listing; the pinned version may be outdated. The
  signature of `lector.com` was not verified separately (it is a copy of `lector-cli.exe`).
* **Linux**: `scripts/sign-linux.sh` was run locally with throw-away keys (detached signatures, embedded `.rpm`
  signature, with and without passphrase).
* **minisign**: `scripts/gen-update-key.sh` and `scripts/sign-checksums.sh` were run locally with minisign 0.11,
  and a signature made by that tool is a test fixture of the Rust verifier.
* **Package managers**: the cask passes `ruby -c` only (no `brew audit`); the winget manifests validate against the
  1.6.0 schemas only; the Flatpak manifest was not built.
* **Pinning**: actions are pinned by commit SHA (resolved with `git ls-remote` on the tags; the GitHub API was not
  reachable, so check the trailing version comments on the next bump), `appimagetool` 1.9.1 and `wingetcreate` are
  pinned by SHA-256 computed from the real release assets. The Azure signing client from NuGet could not be downloaded
  where this was written, so its hash is not recorded: set `ARTIFACT_SIGNING_CLIENT_SHA256` (see above).
* **Job split and environments** were checked by parsing the YAML and `shellcheck` on every bash step, not by running
  them: the first real run (a `dry_run` + `sign_dry_run` run with the `release` environment configured) is the test of
  the artifact hand-offs between the new jobs and of the approval flow.
* Windows signing uses a client secret; federated (OIDC) credentials would avoid a long-lived secret.
